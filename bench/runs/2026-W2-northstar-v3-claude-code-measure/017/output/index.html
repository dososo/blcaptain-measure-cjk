团队 Git 使用规范

统一分支命名、提交信息和代码评审流程，让历史记录可读、可追溯，让每一次合并都经过检查。

  • 版本 1.0
  • 适用于所有业务仓库

1适用范围

本规范适用于团队维护的全部代码仓库，包括前端、后端、脚本和基础设施配置。新成员入职第一周内需要读完本文，并在第一次提交 PR 前对照检查一遍。

规范里的“必须”是硬性要求，CI 或分支保护会拦截违规操作；“建议”是推荐做法，评审时可以提出，但不阻塞合并。

2分支命名

分支模型

我们采用以 main 为主干的短分支模型。所有改动都从 main 拉出功能分支，完成后通过 PR 合并回 main，分支存活时间建议不超过 3 个工作日。

分支用途保护规则
main主干，随时可发布禁止直接推送；只能通过 PR 合并；CI 必须通过
release/*发布分支，冻结版本做回归测试只接受修复类提交；由发布负责人合并
功能分支日常开发，按下文格式命名合并后自动删除

命名格式

<类型>/<任务编号>-<简短描述>

任务编号对应项目管理系统里的需求或缺陷单号，没有单号的小改动可以省略编号。简短描述用英文小写单词，单词之间用连字符连接，说清楚这个分支要做什么。

类型含义示例
feat新功能feat/PAY-142-refund-entry
fix缺陷修复fix/PAY-158-order-total-rounding
hotfix线上紧急修复，从发布标签拉出hotfix/PAY-201-login-timeout
refactor重构，不改变行为refactor/split-user-service
chore依赖升级、构建脚本、配置调整chore/bump-node-22
docs只改文档docs/api-error-codes
release发布分支release/2.8.0

命名约束

  • 必须全部使用小写字母、数字和连字符，任务编号保持系统里的原样大小写。
  • 必须以上表中的类型开头，CI 会校验分支名，不符合的分支无法创建 PR。
  • 不要使用中文、空格、下划线或个人名字，例如 zhang/test、fix_bug。
  • 描述部分控制在 2–5 个单词，过长说明这个分支做的事情太多，应该拆分。
推荐 
feat/PAY-142-refund-entry
fix/login-redirect-loop
避免 
Feature/RefundEntry
fix_bug
wang-dev-1026

3提交信息

提交信息遵循 Conventional Commits 约定。统一的格式让我们可以自动生成更新日志、判断版本号，也方便日后用 git log 和 git blame 追查问题。

格式

<类型>(<范围>): <标题>
                                ← 空一行
<正文>
                                ← 空一行
<脚注>

标题行必须写；正文和脚注按需要写。范围是可选的，填写受影响的模块名，例如 order、auth、ci。

类型

类型何时使用是否进入更新日志
feat新增用户可感知的功能是
fix修复缺陷是
perf性能优化是
refactor重构，既不修缺陷也不加功能否
test新增或修改测试否
docs只改文档或注释否
style格式调整，不影响代码逻辑否
build构建系统、依赖变更否
ciCI 配置和脚本否
chore其他不涉及源码和测试的杂项否
revert回滚之前的提交视情况

写法要求

  • 标题：用中文或英文均可，同一个仓库内保持一致。说明“做了什么”，用动词开头，例如“修复”“新增”“移除”。中文标题不超过 30 个字，英文不超过 50 个字符，结尾不加句号。
  • 正文：说明“为什么改”和“改了之后有什么影响”，而不是逐行复述代码。每行不超过 72 个字符，中文按每行 36 个字左右换行。
  • 脚注：关联任务写 Refs: PAY-142，关闭缺陷写 Closes: #318。有不兼容改动时，必须写 BREAKING CHANGE: 并说明迁移方法，同时在类型后加 !。
  • 一个提交只做一件事。格式化和逻辑改动分成两个提交，方便评审和回滚。
  • 不要提交 wip、update、fix bug 这类没有信息量的标题。本地临时提交在发起 PR 前用 git rebase -i 整理掉。

示例

推荐 
fix(order): 修复优惠券叠加后金额为负

满减券和折扣券同时使用时，先折扣后满减
会导致应付金额小于 0。改为先满减再折扣，
并在结算时把下限钳制为 0。

Closes: #318
避免 
修改了一些东西

fix bug

update order.ts

不兼容改动的写法：

feat(api)!: 订单列表接口改为游标分页

BREAKING CHANGE: /v2/orders 不再接受 page 参数，
请改用 cursor 和 limit。旧参数会返回 400。

Refs: PAY-177

仓库已配置 commitlint 的 commit-msg 钩子。首次克隆后运行一次 npm install（或对应语言的初始化脚本）即可启用；不符合格式的提交会在本地被拦下。

4代码评审

所有进入 main 的代码都必须经过评审。评审的目的是发现缺陷、分享知识、保持代码风格一致，而不是考核个人。

流程

  1. 自查

    发起 PR 前先在本地跑通测试和 lint，把分支 rebase 到最新的 main，自己从头到尾读一遍 diff。

  2. 创建 PR

    按 PR 模板填写：改动背景、实现方式、测试方法、截图或录屏（涉及界面时）、风险和回滚方案。还没准备好的改动用草稿 PR。

  3. 指派评审人

    CODEOWNERS 会自动指派模块负责人；你可以再加一位熟悉相关代码的同事。

  4. 评审

    评审人在 1 个工作日内给出第一轮意见。超过时限可以在团队群里提醒，或者改派其他人。

  5. 修改与回复

    作者逐条回复评论：已修改的附上提交链接，不同意的说明理由。由提出意见的人确认后再标记为已解决。

  6. 合并

    满足合并条件后由作者本人合并，合并后确认分支已删除、关联的任务状态已更新。

PR 要求

  • 单个 PR 的有效改动建议不超过 400 行（不含自动生成的代码和锁文件）。更大的改动拆成多个依次合并的 PR。
  • PR 标题沿用提交信息的格式，例如 feat(order): 支持部分退款，合并时会作为压缩提交的标题。
  • 描述里必须关联任务编号，并写清楚评审人应该重点看哪里。
  • CI 未通过的 PR 不进入评审，作者先自行修复。

评审人守则

评论时用前缀标明意见的分量，让作者知道哪些必须改：

前缀含义是否阻塞合并
[必须]缺陷、安全问题、违反规范，不改不能合并是
[建议]更好的写法或设计，作者可以自行决定否
[疑问]没看懂，需要作者解释视回答而定
[细节]命名、措辞等小问题否

评审时按下面的清单检查：

  • 改动是否解决了任务描述里的问题，有没有遗漏的边界情况
  • 是否有对应的测试，测试是否真的覆盖了改动的逻辑
  • 错误处理、日志和监控是否完整
  • 有没有硬编码的密钥、地址或个人信息
  • 数据库迁移、配置变更是否可以回滚
  • 命名和结构是否与周围代码一致

评论针对代码，不针对人。指出问题时尽量给出具体的修改方向；看到写得好的地方，也可以直接说出来。

合并规则

条件要求
批准人数至少 1 人批准；支付、权限、数据迁移相关目录至少 2 人批准
CI全部检查通过
评论所有 [必须] 评论已解决
合并方式默认使用 Squash and merge；release/* 回合到 main 时使用 Merge commit
分支同步与 main 有冲突时由作者 rebase 解决，不在 PR 里合入 main

线上紧急修复可以先合并、后补评审，但必须在 24 小时内补齐评审记录，并在 PR 描述里写明原因。

5常见问题

提交信息写错了怎么办？

还没推送的最后一个提交，用 git commit --amend 修改；已经推送到功能分支的，用 git rebase -i 修改后执行 git push --force-with-lease。永远不要对 main 强制推送。

功能分支落后 main 很多怎么办？

在功能分支上执行下面的命令，解决冲突后再推送：

git fetch origin
git rebase origin/main
git push --force-with-lease

评审意见有分歧时听谁的？

先在 PR 里讨论，两轮仍无共识时拉上模块负责人当面或语音沟通，结论写回 PR 评论里。涉及架构的分歧，提到周会上讨论。

规范本身需要修改怎么办？

欢迎提交 PR 修改本文档，按普通代码评审流程走，需要至少 2 人批准。

本规范由研发团队共同维护，最后更新于 2026 年 10 月。
