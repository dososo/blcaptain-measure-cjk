### SA-01 · High · 红框标签上的数值不是截图里那个宽度下的实测值

- **位置：** `bench/showcase-build.mjs` 第 96–99 行（`label()` 从 `f.message` 里取数）、第 94 行（`atWidth` 过滤）；`site/shots/real-*-control.jpg`；展示页「真实页面」一节的说明「标签是规则编号和实测值」。
- **问题：** 完整档会把同一个元素在各个宽度下的结论合并成一条，`message` 里的数值是**第一个出问题的宽度**（通常是 360px，有时是 768px）量到的。截图却是在 1280px 下截的。字号用了 `cqw`、`@media`，或者随宽度变化的元素，标签和画面就对不上。我在截图用的同一个渲染环境里，逐个元素重新量了一遍：
  - 画进图里的 46 个标签，有 25 个数值不对；
  - 026（小红书卡片）的 16 个标签全部偏小：标的是 8.3px、8.6px、9.7px，图里实际是 10.96px、11.33px、12.84px；
  - 008 第一个红框标「T11 · 8.0px」，图里实际是 10px。CSS 里 8px 只在 `@media(max-width:700px)` 生效；
  - 011 有 4 个框标 10px，图里实际是 11px；标题的 2 个 T07 框标 −1px，图里实际是 −1.5px；
  - 004 的 2 个 T07 框标 −0.64px，图里实际是 −1.152px（57.6px 的标题）。
  - 同一组图前后自相矛盾：026 的图注写「最小中文字号 11px」，标签却是 8.3px；008 的图注写最小 9px，第一个标签却是 8.0px。
- **为什么是问题：** 页面明确说标签是「实测值」。读者拿标签对照图片，会发现数值对不上，展示页的可信度会受影响。这一节是给外部看的证据，不能有对不上的数字。
- **修法：** 标签数值在截图那次渲染里当场量：
  - T11 取元素内含汉字的文字节点里最小的 `font-size`；
  - T07 取 `letter-spacing` 的计算值；
  - T05 按实际折行数字数。

  当场量到的值如果已经不违规（例如 026 的 `p.sub` 在 1280px 下是 12.84px），就要按规则阈值重新判断要不要画框。另外加一条自检：标签值和图注里的最小字号不能互相矛盾，自检失败就让构建停下。

### SA-02 · High · 小红书卡片那组对比的显示比例不一样，页面对截图方式的描述也不对

- **位置：** `bench/showcase-build.mjs` 第 30 行 `VIEW.card = { width: 1280, height: 1440 }`；`site/shots/real-claude-code-026-*.jpg`；展示页说明「小红书卡片按 1080×1440 的导出尺寸截」；图注「最小中文字号 11px」和「26px」。
- **问题：**
  - 不装 measure 那版卡片写的是 `width: min(100%, 540px); aspect-ratio: 3/4`，也就是一张 540×720 的预览卡。装了 measure 那版是 1080×1440。两张都放进 1280×1440 的画布：前者只占画面中间 42% 的宽度，后者铺满整个宽度。
  - 页面说「按 1080×1440 的导出尺寸截」。实际画布是 1280×1440，不装那版的卡片也不是 1080 宽，这句话两头都不对。
  - 图注拿两张设计宽度不同的卡片比 CSS px（11px 对 26px）。按「字号占卡片宽度的比例」算，是 10.96/540 = 2.03% 对 26/1080 = 2.41%。两张卡都导出成 1080 宽的图，最小字分别约是 22px 和 26px。差别是有的，但远没有「11 → 26」看上去那么大。
  - 手机上这组还被排成两列，见 SA-08。
- **为什么是问题：** 「装之前又小又挤、装之后又大又清楚」的印象，主要来自显示比例不同，不是来自 measure。这正是用户点名要查的口径公平问题。对外展示里，这种视觉上的夸大和文字上的夸大一样会误导读者。
- **修法（任选其一，并改掉说明文字）：**
  - ① 两版都按卡片自身的边框裁切，再缩放到同一显示宽度：不装那版用 `deviceScaleFactor: 2` 截 540 宽的卡片，得到 1080 宽的图；
  - ② 换一组不是卡片的页面。

  图注里的最小字号，要么改成「占卡片宽度的比例」，要么写明两版卡片的设计宽度不同（540 和 1080）。说明文字改成实际的截图方式。
- **证据：** 见 SA-01 的探针输出：`card … "w":540,"h":720` 对 `card {"tag":"DIV.card","w":1080,"h":1440,"x":0,"y":0}`。卡片 CSS 是 `width: min(100%, 540px); aspect-ratio: 3 / 4; … container-type: inline-size;`。提示词原文：「做一张小红书风格的图文卡片（HTML，竖版 3:4）…」，没有指定尺寸。

### SA-03 · High · 4 组真实页面都挑自对照组问题最多的前四分之一，页面没有说明怎么挑的

- **位置：** `bench/showcase-build.mjs` 第 22–27 行 `PAIRS`；展示页「真实页面」一节。
- **问题：** 按「排除 T02、T04 后对照组的 error 条数」排名：
  - codex 008、011 都是 34 条，并列 30 页里第 4 名（中位数 24）；
  - claude 026 有 16 条，排第 5；004 有 9 条，排第 7。claude 对照组有 15/30 页本来就是零 error，中位数只有 0.5。

  4 组的「装了之后」全部是 0 error。展示页没有一组是「不装也已经很好」，也没有 claude 实验组里没修干净的页（028：20 → 3；012：1 → 4，更差）。页面和提交说明都没有写挑选标准。
- **为什么是问题：** 这一节的标题是「同一条提示词，装之前和装之后」，读者会把它当作典型情况。数字区写着 claude 是 15/30 → 27/30，可图例全是「错很多 → 全对」，两者给人的印象不一样。挑问题多的页面便于看出差别，这本身可以接受，但必须明说，否则就是用户问的「挑得过于有利」。
- **修法：**
  - 必做：在这一节开头写明挑选标准和这几组在分布里的位置。例如：「挑的是不装时问题较多、肉眼看得出差别的页面：codex 两组在 30 页里排第 4，claude 两组排第 5、第 7。claude 不装时，有一半页面除 T02、T04 外本来就零 error。」
  - 建议：加一组 claude 028（20 → 3，没修干净），或者 012（更差）作为反例。
  - 挑选标准写进 `showcase.json`，由脚本算出排名，不要手填。
- **证据（审计方命令 C11）：**

  ```

     011 control 34 rank 4 /30
  claude-code median 0.5 zeroCtrl 15 measureNonzero 012:1→4,019:0→1,028:20→3

### SA-04 · Medium · 图注计数漏了 lint 省略的处数；「34 条 error」里有 12 条是页面自己说有误报的 T06

- **位置：** `site/_build.mjs` 第 46–51 行，以及 `showcase-build.mjs` 第 85–86 行的 `counts`、`errors_excl_own`。
- **问题：**
  - ① 完整档每条规则最多列出若干处，其余合并成一条「同一条规则在本页另有 N 处，已省略」。脚本把这一条也当成「1 处」。所以 011 的图注写「T11（字号太小）20 处」，实际是 19 + 32 = 51 处；008 写「21 处」，实际是 24 处。红框也只能标出列出的那些，所以 011 的「团队版」一栏一个框都没有，看上去像是没问题。
  - ② 011 图注的「34 条 error」里有 12 条 T06，全是单行 `li` 行高 1.45。这正是北极星审计 NA-05 判为误报的模式。页面在上一段自己说了 T06 有误报、不标，但图注照样把它们算进去，也没有提示。
- **为什么是问题：** 「处」是给读者看的位置数，写错就是数字不实，虽然这里是少报。「34 条」和 `results.json` 的口径一致，这没错，但和页面自己的误报说明放在一起，前后不一致。
- **修法：** 「处」按「列出的 + 省略的」算；图注加一句「lint 每条规则最多列出 N 处，红框只标列出的」。011 的图注写成「34 条 error（其中 T06 12 条，属于正在修的误报）」，或者另给一个不含 T06 的数。
- **证据：**

  ```

  codex-control/011/lint-render.json {"errors":36,…} findings_err 36 omitted-lines ["T11:同一条规则在本页另有 32 处，已省略"]
  T06 360 section#plans… > ul.featur… | 正文行高 1.45（计算值 17.4px ÷ 字号 12px），低于 1.5。   ×12
  ```

### SA-05 · Medium · 字体核对用的是黑名单，没收录的字体一律放行

- **位置：** `bench/showcase-lib.mjs` 第 46 行 `SYSTEM_CJK`、第 112–116 行 `violations`、第 89–93 行 `walk`。
- **问题：**
  - ① 判定规则是「名字匹配 `SYSTEM_CJK`」或者「在授权表里且 `commercial_image !== true`」才算不合格。授权表里查不到的字体（`matchFontName` 返回 null）直接放行。本机就装着 `Arial Unicode`（Monotype 授权，含汉字字形）、`AppleGothic`、`AppleMyungjo`（含汉字字形），它们既不在 `SYSTEM_CJK` 里，也不在授权表里。名单还漏了 STFangsong、BiauKai、Yu Gothic、Osaka 等。用户自己装的字体，如果页面点名，也会被放行。
  - ② `walk` 只遍历 `children`、`pseudoElements`、`shadowRoots`，不进 `contentDocument`（iframe）和 `templateContent`。
  - ③ `canvas` 里画的字、以 `<img>` 引用的 SVG 里的字，都查不到，也不会被替换。

  这次的 8 个页面里，我 grep 过 `iframe`、`canvas`、`<img …svg` 都是 0，`showcase.json` 的记录里汉字也确实只来自 Noto。**所以这次的截图没有越界**，问题在于核对方法本身有漏洞。
- **为什么是问题：** 页面写「截图后逐个元素核对过实际用到的字体」，读者会理解成「只用了允许的字体」。黑名单只能证明「没用到已知的坏字体」。以后换页面或换机器，可能悄悄混进来。
- **修法：** 改成白名单。
  - 汉字字形只允许 `Noto Sans SC*`、`Noto Serif SC*`。按文字节点所在的书写系统分开核对，或者对含汉字的元素单独断言。
  - 非汉字字体列一份显式的允许清单（见 SA-06），清单外的一律判为不合格。
  - `walk` 补上 `contentDocument` 和 `templateContent`。
  - 页面里有 `canvas`、SVG 图片时直接报错，或者在报告里标出来。
- **证据：**

  ```
  $ node -e 'matchFontName(…)'
  Arial Unicode MS 未收录 / STFangsong 未收录 / Yu Gothic 未收录 / Osaka 未收录 / Apple Color Emoji 未收录 / Menlo 未收录 / .SF NS 未收录 …
  $ ls /System/Library/Fonts … | grep …
  Arial Unicode.ttf  AppleGothic.ttf  AppleMyungjo.ttf  STHeiti Light.ttc  Songti.ttc …
  008/011/004/026 control+measure: iframe=0 canvas=0 imgsvg=0 svgtext=0
  ```

### SA-07 · Medium · 示意 T06 的「关」比实验里任何一个真实页面都差；T07 也偏重

- **位置：** `site/demos/_gen.mjs`：T06 `off: line-height: 1.2`，T07 `off: letter-spacing: -0.06em`。
- **问题：**
  - 60 页对照组里，T06 的 error 只有三种：行高 1.45（12 条）、1.35（6 条）、多行却没设行高（5 条）。没有一页是 1.2。浏览器的默认值（Noto Sans SC 的 `normal` 约 1.45）本身就会被 T06 报出来。
  - T07 的真实计算值在 −0.2 到 −2.7px 之间。008 是 66.6px 的标题配 −2px，约等于 −0.03em。示意用的是 40px 配 −0.06em（−2.4px），比例上是真实情况的 2 倍左右。
  - 其余 5 组，「关」的取值都在真实范围之内：T02 是浏览器默认，T03 用半角标点，T05 每行 52 字（真实 56–59），T08 合成斜体，T11 是 10px（真实 8–11px）。
- **为什么是问题：** 用户要求核对「关」那版是不是人为做得比真实情况更糟。T06 是，T07 轻微是。虽然页面标了「示意」，但它们的作用是让读者形成「这条规则管的是什么」的直觉。夸张的「关」会让人高估真实页面的问题。
- **修法：** T06 的「关」改成 1.35 或 1.4（实验里真实出现过的值，lint 一样报）。T07 改成 −0.03em（008 的真实比例）。改完重新跑 `showcase-build.mjs` 的验证。
- **证据（审计方命令 C12）：**

  ```

### SA-08 · Medium · 手机上卡片那组还是两列，真实截图上的标签看不清

### SA-09 · Medium · 红框标签遮住了被标出来的文字

- **位置：** `showcase-build.mjs` 第 116–118 行。标签固定放在框上方 22px 处，背景是不透明的。
- **问题：** 元素一个挨一个时，标签会盖住上一个元素的文字。011 的「免费版」「专业版」标题和「¥0」「¥29」被盖住了一部分，功能列表前三行被盖住。026 每张小卡片的步骤 1、2 行，几乎整行被标签盖住。读者正好看不到被指出问题的那些小字。
- **为什么是问题：** 红框的作用是让读者亲眼看到问题，标签把证据本身挡住了。
- **修法：** 标签放到框内右上角，或者放在页边、用连线连到框上。相邻的同类问题合并成一个框，例如「T11 × 3 · 10.96px」。标签背景改成半透明，或者只描边。

### SA-10 · Low · alt 文字太笼统，有一处不准

### SA-11 · Low · 规则示意没说明哪些规则没做、为什么；T04 的理由经实测成立

- **位置：** 展示页「规则示意」一节；`site/demos/_gen.mjs`。
- **问题：** error 级规则有 10 条：T01–T08、T11、T13。示意只做了 7 条，T01、T04、T13 没做，页面没有说明。用户的要求是「每条规则做一组」，没做的应该写明原因。
- **T04 的理由核验结论：成立。** 我用系统 Chrome 155 实测：同一段中文在 80–520px 的 441 个宽度下，`line-break: auto` 和 `strict` 两种设置都不会把 ，。、：；？！… ～ 放在行首。两者只有 64 个宽度不一样，差别全部来自 U+301C「〜」、日文长音「ー」这类字符；中文里常用的全角波浪号 U+FF5E「～」两种设置都会放在行首。所以常见中文标点开不开确实看不出差别，执行方的理由成立。顺带发现：「——」在两种设置下都会被拆到两行。这属于另一条规则（T17）的范围，记在这里备查。
- **修法：** 在这一节末尾加一句：「T01（lang）、T04（行首禁则）、T13（字体栈）在 Chrome 里的效果肉眼难以区分，或者依赖访客电脑上装了什么字体，所以不做示意」。
- **证据（审计方命令 C13）：**
