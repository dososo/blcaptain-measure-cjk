0基本原则

  • main 永远可发布。禁止直接推送，所有变更通过 Pull Request（PR）合入。
  • 小步提交，小步合并。一个分支只做一件事，一个 PR 尽量控制在 400 行有效改动以内。
  • 历史是写给人看的。分支名、提交信息、PR 描述都应让半年后的同事看懂“改了什么、为什么改”。
  • 自动化优先。能由 CI、lint、钩子检查的，不依赖人工记忆。

1分支命名

我们采用基于主干的轻量分支模型：短生命周期的功能分支从 main 拉出，完成后通过 PR 合回。

分支模型

分支用途来源 → 去向生命周期
main主干，始终保持可发布状态—永久
feature/*新功能开发main → main建议 ≤ 5 个工作日
fix/*常规缺陷修复main → main短期
hotfix/*线上紧急修复release/* 或 tag → 发布分支 + main当天
release/*版本发布准备、冻结后只接收修复main → 打 tag到版本结束
refactor/* docs/* chore/*重构、文档、构建与杂项main → main短期

命名格式

<类型>/<工单号>-<简短描述>

feature/PROJ-123-user-login
fix/PROJ-456-null-avatar-crash
hotfix/PROJ-789-payment-timeout
release/2.4.0
  • 全部使用小写字母、数字和连字符 -，不使用空格、下划线、中文或大写字母。
  • 有工单的必须带上工单号，便于和任务系统自动关联；无工单可省略。
  • 描述部分 2～5 个英文单词，说明“做什么”，而不是“谁在做”。
  • release/ 后直接跟语义化版本号，如 release/2.4.0。
  • 分支合并后立即删除（远端开启“合并后自动删除分支”）。
✓ 推荐
  • feature/PROJ-123-export-csv
  • fix/PROJ-88-date-timezone
  • docs/update-onboarding
✗ 避免
  • zhangsan-dev（以人命名）
  • Feature/ExportCSV（大小写混用）
  • fix_bug、test2（无意义）

2提交信息

提交信息遵循 Conventional Commits 约定，可直接用于生成 CHANGELOG 和判断版本号。

格式

<type>(<scope>): <subject>
                                  ← 空一行
<body：说明为什么改、怎么改，每行 ≤ 72 字符>
                                  ← 空一行
<footer：关联工单、不兼容变更说明>

示例：

feat(auth): 支持手机号验证码登录

原有登录仅支持账号密码，移动端用户转化率偏低。
新增短信验证码通道，验证码 5 分钟有效，同一号码
60 秒内限发一次。

Refs: PROJ-123
fix(order)!: 订单金额统一使用分为单位

BREAKING CHANGE: /api/orders 返回的 amount 字段由元（浮点）
改为分（整数），调用方需同步调整。

Closes: PROJ-456

类型（type）

type含义是否进入 CHANGELOG
feat新功能是（次版本号 +1）
fix缺陷修复是（修订号 +1）
perf性能优化是
refactor重构，不改变外部行为否
docs仅文档变更否
test新增或修改测试否
style格式调整（空格、分号等），不影响逻辑否
build / ci构建系统、依赖、CI 配置否
chore其他杂项否
revert回滚某次提交视情况

在 type 后加 ! 或在 footer 写 BREAKING CHANGE: 表示不兼容变更（主版本号 +1）。scope 为可选的模块名，如 auth、order、ui，团队在各仓库 README 中维护可用列表。

书写规则

  • subject 不超过 50 个字符（中文约 25 字），用祈使语气描述“做了什么”，结尾不加句号。
  • body 解释动机和取舍，而不是复述 diff；简单变更可省略。
  • 一次提交只做一件事。格式化与逻辑修改分开提交；不要把无关改动顺手塞进来。
  • 每次提交都应能通过编译和测试，便于 git bisect 定位问题。
  • 推送前用 git rebase -i 整理本地的 “wip”“fix typo” 类提交；已推送且他人基于其开发的分支禁止强推，自己的功能分支可用 --force-with-lease。
  • 不要提交密钥、账号、本地配置和构建产物；善用 .gitignore。
✓ 推荐
  • fix(cart): 修复数量为 0 时仍可下单的问题
  • refactor(user): 拆分 UserService 中的鉴权逻辑
✗ 避免
  • update、修改、fix bug
  • feat: 改了好多东西，顺便修了几个 bug。
自动校验：仓库通过 commitlint + Git hooks（如 husky / lefthook）在本地校验提交信息格式，CI 中也会对 PR 标题做同样检查。

3代码评审流程

代码评审的目标是提升代码质量、分享知识、减少风险，而不是挑人毛病。所有合入 main 的代码都必须经过评审。

流程

  1. 开分支、开发、自测从最新的 main 拉出分支；本地运行 lint 与测试，确保通过。
  2. 创建 PRPR 标题遵循提交信息格式（合并时作为 squash 提交信息）；按模板填写描述。尚未完成的工作请标记为 Draft。
  3. CI 检查构建、单元测试、lint、安全扫描全部通过后，才请求评审。
  4. 指派评审者至少 1 名评审者；涉及核心模块、数据库变更、安全相关的改动需 CODEOWNERS 中的负责人批准。
  5. 评审与修改评审者在 1 个工作日内给出首次反馈；作者逐条回复或修改，修改以新提交追加，便于复查。
  6. 批准与合并获得批准、所有讨论已解决、CI 通过后，由作者本人合并并删除分支。
  7. 上线验证合并后关注部署和监控，确认无异常后关闭工单。

作者职责

PR 描述模板：

## 背景
为什么要做这个改动？关联工单：PROJ-123

## 改动内容
- 主要改了什么
- 有哪些设计取舍

## 测试方式
如何验证？覆盖了哪些场景？（附截图/录屏，如涉及 UI）

## 风险与回滚
是否涉及数据迁移、配置变更、不兼容改动？如何回滚？
  • PR 聚焦单一目的，改动量尽量 ≤ 400 行；超大改动提前拆分或先发设计讨论。
  • 提交前自己先完整看一遍 diff，删除调试代码和无关改动。
  • 为新逻辑补充测试，为不直观的代码写注释。
  • 对评审意见逐条回应：已修改、给出理由，或另开工单跟进。
  • 不要在评审进行中强推改写历史，以免评审者丢失上下文。

评审者职责

评审时重点关注：

维度关注点
正确性逻辑是否符合需求，边界条件、异常和并发是否处理
设计职责划分是否合理，是否过度设计或引入不必要的依赖
可读性命名清晰、结构易懂，后来者能否快速理解
测试关键路径是否有测试，测试是否真正验证了行为
安全与性能输入校验、权限、敏感信息、N+1 查询、资源泄漏等

评论时使用前缀标明意图，让作者清楚哪些必须改：

前缀含义是否阻塞合并
[必须]缺陷、安全问题或违反规范，必须修改是
[建议]更好的写法，作者可自行判断否
[疑问]需要作者解释的地方视回答而定
[小问题]命名、拼写等细节否
评审礼仪：对事不对人；多提问题少下结论（“这里如果传入空列表会怎样？”优于“这里写错了”）；看到好的写法也请点赞。风格类争议以 lint 规则为准，不在评审中反复争论。

合并规则

  • main 开启分支保护：禁止直接推送与强推，要求 CI 通过、至少 1 个批准、所有讨论已解决。
  • 默认使用 Squash and merge，合并后的提交信息即 PR 标题 + 关键描述；需要保留多个有意义提交时可用 Rebase and merge。
  • 合并前分支需与 main 同步（rebase 或合并最新 main）并重新通过 CI。
  • hotfix 可在 1 名评审者口头确认后先合并，但须在 24 小时内补全评审记录。
  • PR 超过 3 个工作日无进展，作者需在团队频道同步状态或关闭。

4常用命令速查

# 开始新任务
git switch main && git pull --rebase
git switch -c feature/PROJ-123-user-login

# 提交
git add -p                          # 按块挑选要提交的改动
git commit                          # 在编辑器中书写完整提交信息

# 推送前整理本地提交
git fetch origin
git rebase -i origin/main

# 推送（首次）/ 整理后更新自己的分支
git push -u origin HEAD
git push --force-with-lease

# 合并后清理
git switch main && git pull --rebase
git branch -d feature/PROJ-123-user-login
git fetch --prune
推荐全局配置：git config --global pull.rebase true、git config --global fetch.prune true、git config --global init.defaultBranch main。
