团队 Git 使用规范

统一分支命名、提交信息和代码评审流程，让每一次改动都可追溯、可评审、可回滚。

适用范围：团队所有代码仓库 · 版本 1.0

一总则

  • 主干受保护：main 禁止直接推送，所有改动经 Pull Request（下称 PR）合入。
  • 小步提交：一个分支只做一件事，一个提交只表达一个意图。
  • 历史可读：提交信息写给半年后的同事看，而不是写给现在的自己。
  • 评审必经：至少一位非作者成员批准，且 CI 全部通过后才能合并。
  • 不提交密钥：密码、Token、证书一律不进仓库；误提交后立即吊销，不能只删文件了事。

二分支命名

长期分支

分支用途规则
main随时可发布的稳定代码受保护；仅通过 PR 合入；每个发布打 tag
release/x.y维护中的历史版本（可选）只接受修复，修复需同步回 main

短期分支格式

<类型>/<工单号>-<简短描述>
类型场景示例
feat新功能feat/PROJ-128-user-export
fix缺陷修复fix/PROJ-342-login-timeout
hotfix线上紧急修复hotfix/PROJ-401-payment-crash
refactor重构，不改行为refactor/PROJ-215-order-service
docs仅文档docs/PROJ-87-api-guide
chore构建、依赖、配置chore/PROJ-90-upgrade-node

命名要求

  • 全部小写，单词之间用连字符 -，不用下划线、空格或中文。
  • 描述部分 2–5 个英文单词，总长不超过 50 个字符。
  • 没有工单的改动可省略工单号，如 chore/update-gitignore。
  • 分支合并后由作者删除；超过 30 天无活动的分支会被清理。
推荐
feat/PROJ-128-user-export
避免
Zhang_test2
新功能-导出

三提交信息

采用 Conventional Commits 1.0.0 格式，方便自动生成变更日志和判断版本号。

格式

<type>(<scope>): <subject>

<body>

<footer>
部分要求
type必填。feat fix refactor perf docs test build ci chore revert
scope可选。受影响的模块，如 auth、order
subject必填。祈使句，说明「做了什么」；不超过 50 字符；结尾不加句号
body改动不显而易见时必填。说明「为什么改」和「怎么改」，每行不超过 72 字符
footer关联工单 Refs: PROJ-128；破坏性变更写 BREAKING CHANGE: ...

示例

fix(auth): 刷新 token 前校验过期时间

旧逻辑在 token 已过期时仍尝试刷新，导致 401 循环重试。
改为先比较 exp 字段，过期则直接跳转登录页。

Refs: PROJ-342
推荐
feat(order): 支持按日期导出订单
docs: 补充本地开发环境说明
避免
update
fix bug
改了点东西。

提交习惯

  • 一个提交只做一件事；格式化与逻辑改动分开提交。
  • 每个提交都应能通过编译和测试，便于 git bisect 定位问题。
  • 推送前用 git rebase -i 整理本地的「wip」「typo」类提交。
  • 已推送且他人在用的分支不要强推；确需强推用 git push --force-with-lease。

四代码评审流程

  1. 同步主干

    发起前执行 git fetch && git rebase origin/main，解决冲突并确保本地测试通过。

  2. 发起 PR

    标题沿用提交信息格式；描述写清背景、改动点、测试方式，UI 改动附截图。未完成的工作标记为 Draft。

  3. CI 检查

    构建、单元测试、Lint、安全扫描全部通过后再请求评审，不让评审者替 CI 找问题。

  4. 指派评审

    至少 1 位评审者；涉及核心模块、数据库迁移或安全相关代码需 2 位，其中一位为模块负责人（CODEOWNERS）。

  5. 评审与修改

    评审者在 1 个工作日内首次响应。作者逐条回复评论，修改以新提交推送，便于评审者查看增量。

  6. 批准合并

    全部评论已解决、获得批准、CI 通过后，由作者本人合并，合并后删除分支。

PR 大小

单个 PR 建议不超过 400 行有效改动。超出时拆分为多个可独立评审的 PR，或先合入不对外暴露的基础改动。

评审关注点

  • 正确性：逻辑、边界条件、异常处理、并发问题。
  • 安全：输入校验、权限检查、敏感信息泄露。
  • 可维护性：命名、结构、重复代码、是否过度设计。
  • 测试：新增逻辑有对应测试，修复的缺陷有回归测试。
  • 兼容性：接口、配置、数据结构变更是否影响现有调用方。

评论约定

前缀含义是否阻塞合并
[必改]缺陷、安全问题、违反规范是
[建议]更好的写法，作者可自行判断否
[疑问]需要作者解释意图回复前阻塞
[小问题]命名、格式等细节否
评审对事不对人。评论指向代码而不是作者，说明原因并尽量给出替代方案；讨论超过三轮未达成一致时，改为当面或语音沟通，结论回写到 PR 中。

五合并与发布

  • 默认使用 Squash and merge，合并后的提交信息按第三节格式整理。
  • 提交本身已整理干净、需要保留每一步历史时，可用 Rebase and merge。
  • 发布时在 main 上打语义化版本 tag，如 v2.3.0；含 BREAKING CHANGE 时升主版本号。
  • 热修复从 main（或对应 release/x.y）拉 hotfix/* 分支，同样走 PR，可将评审人数降为 1 位，但不可跳过 CI。
  • 回滚使用 git revert 生成新提交，不在公共分支上 reset 历史。

六速查

# 从最新主干拉分支
git switch main && git pull --rebase
git switch -c feat/PROJ-128-user-export

# 提交
git add -p
git commit -m "feat(order): 支持按日期导出订单"

# 推送前同步主干、整理提交
git fetch origin
git rebase -i origin/main

# 推送（首次）
git push -u origin feat/PROJ-128-user-export

# 必须强推时
git push --force-with-lease

# 合并后清理
git switch main && git pull --rebase
git branch -d feat/PROJ-128-user-export
