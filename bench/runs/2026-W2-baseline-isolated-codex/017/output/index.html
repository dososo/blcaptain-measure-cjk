01

分支命名

从最新的 main 创建工作分支，使用小写英文与连字符，让分支名称直接表达意图。

PATTERN<type>/<issue-id>-<short-description>
分支类型使用场景命名示例
feature/新增功能或能力feature/123-user-login
fix/修复常规缺陷fix/246-token-expiry
hotfix/修复线上紧急问题hotfix/307-payment-timeout
refactor/重构代码，不改变外部行为refactor/158-auth-service
chore/文档、依赖与工程配置维护chore/182-update-eslint
ⓘ
保护主分支。 main 应始终可发布，禁止直接推送；通过 PR 合并后删除工作分支。无关联任务时可省略 issue-id。紧急修复从当前生产版本创建，并同步回 main。
02

提交信息

采用 Conventional Commits 格式。每个提交只包含一项逻辑变更，说明“做了什么”。

PATTERN<type>(<scope>): <description>

选择准确的类型 COMMIT TYPES

feat新增功能
fix修复缺陷
docs更新文档
style代码格式
refactor代码重构
test测试变更
perf性能优化
chore工程维护

让变更一目了然 EXAMPLES

✓ feat(auth): 新增邮箱验证码登录
✕ update code / 修复 bug避免没有范围、没有具体含义的描述。
  • scope 可省略；填写时使用模块名，如 auth、api。冒号后留一个空格，标题建议不超过 72 个字符。
  • 复杂变更在空行后的正文说明原因与影响，关联任务可在末尾注明 Refs #123。
  • 不兼容变更使用 feat(api)!: …，并在页脚用 BREAKING CHANGE: 说明影响和迁移方法。
  • 提交前检查暂存区，确保不包含密钥、本地配置、调试代码或无关文件。
03

代码评审流程

所有变更通过 Pull Request（PR）进入主分支。作者对变更负责，评审者共同守护代码质量。

STEP 01 →

自检与提交

检查 diff，运行相关测试与静态检查。拆分过大的变更，确保 PR 聚焦单一目标。

STEP 02 →

创建 Pull Request

标题沿用提交格式。说明背景、方案、验证结果与风险；界面变更附截图，指定评审者。

STEP 03 →

评审与迭代

至少一位非作者批准。逐条回复意见并修正；有新提交时重新确认批准，解决全部阻塞意见。

STEP 04 ✓

合并与清理

确认 CI 通过且无冲突，使用 Squash merge，检查最终提交信息；删除分支并同步本地 main。

合并前，确认这四件事

☑逻辑正确，边界条件与异常处理充分
☑相关测试通过，新增行为有必要的验证
☑命名清晰，变更范围可控，无敏感信息
☑文档同步，风险与回滚方式已说明
↳
评审代码，也尊重彼此。 建议在一个工作日内首次响应。评论说明原因，区分阻塞问题与可选建议；紧急修复仍需评审与必要检查，后续补齐回归测试。
✳
规范的目的，是让协作更轻松。

遇到约定未覆盖的情况，请在 PR 中说明，与团队达成共识后更新本手册。
