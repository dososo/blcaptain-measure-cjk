工程规范

团队 Git 使用规范

统一分支命名、提交信息和代码评审流程，让历史可读、改动可追溯、合并可预期。所有仓库默认遵循本规范，例外情况需在仓库 README 中注明。

适用范围：全部业务仓库 · 版本 v1.0

01总览

  • main 始终可发布，禁止直接推送，只能通过 Pull Request（PR）合并。
  • 所有改动在短生命周期的功能分支上完成，分支存活时间尽量不超过 3 个工作日。
  • 提交信息遵循 Conventional Commits 格式。
  • 每个 PR 至少需要 1 位评审者批准，且 CI 全部通过后才能合并。

02分支命名

分支模型

采用基于主干的轻量模型：main 为唯一长期分支，其余均为从 main 拉出、合并后删除的短期分支。

前缀用途来源 → 合并目标
feat/新功能main → main
fix/缺陷修复main → main
hotfix/线上紧急修复release/* 或 main → 两者都要合回
refactor/重构，不改变外部行为main → main
docs/仅文档改动main → main
chore/构建、依赖、配置等杂项main → main
release/发布准备，只接受修复main → 打 tag 后合回 main

命名格式

<类型>/<工单号>-<简短描述>

feat/PROJ-123-user-login
fix/PROJ-456-null-avatar
release/2.4.0
  • 全部使用小写英文，单词之间用连字符 - 分隔，不使用下划线、空格或中文。
  • 有工单的必须带工单号；没有工单的小改动可省略。
  • 描述控制在 2–5 个单词，能看出改的是什么即可。
  • 发布分支使用语义化版本号：release/主版本.次版本.修订号。
✓ 推荐
  • feat/PROJ-123-export-csv
  • fix/PROJ-88-timezone-offset
  • chore/upgrade-node-20
✗ 避免
  • zhangsan-dev
  • Feature/Export_CSV
  • fix-bug

03提交信息

格式

<type>(<scope>): <subject>

<body>

<footer>

type 和 subject 必填；scope、body、footer 按需填写。完整示例：

fix(auth): 修复 token 过期后未跳转登录页的问题

refresh 接口返回 401 时拦截器直接抛出异常，
导致页面停留在空白状态。现改为清除本地凭证并重定向到 /login。

Closes PROJ-456

type 列表

type含义
feat新增功能
fix修复缺陷
refactor重构（既不新增功能也不修复缺陷）
perf性能优化
docs文档
test新增或修改测试
style代码格式（空格、分号等，不影响逻辑）
build构建系统或外部依赖
ciCI 配置与脚本
chore其他不修改源码和测试的改动
revert回滚某次提交

书写规则

  • subject：说明“做了什么”，不超过 50 个字符（中文约 25 字），结尾不加句号；英文使用祈使句、首字母小写，如 add retry to upload。
  • scope：受影响的模块名，如 auth、order、api，团队内保持一致。
  • body：说明“为什么改”以及与之前行为的差异，每行不超过 72 个字符。
  • footer：关联工单（Closes PROJ-123）；不兼容变更以 BREAKING CHANGE: 开头说明迁移方式，或在 type 后加 !，如 feat(api)!:。
  • 一次提交只做一件事。格式化与逻辑改动分开提交。
  • 推送到共享分支前，用 git rebase -i 整理掉 wip、fix typo 这类零碎提交。
✓ 推荐
  • feat(order): 支持按日期区间导出订单
  • fix(upload): 处理文件名含空格时的编码错误
  • refactor(user): 拆分 UserService 为读写两部分
✗ 避免
  • update
  • 修改了一些东西。
  • fix bug and add feature and refactor
工具建议：仓库可接入 commitlint + husky 在本地 commit-msg 钩子中校验格式，CI 中再校验一次 PR 标题。

04代码评审

流程

  1. 同步主干从最新的 main 拉出分支；开发过程中定期 git rebase origin/main，保持分支与主干接近。
  2. 自测并自审本地跑通测试和 lint，提 PR 前先自己把 diff 完整看一遍。
  3. 创建 PR标题沿用提交信息格式；按模板填写描述，并指定 1–2 位评审者。未完成的工作以 Draft 状态提交。
  4. 评审评审者在 1 个工作日内给出首轮反馈；提交者逐条回复或修改。
  5. 批准并合并获得批准且 CI 通过后，由提交者本人合并，并删除远程分支。

提交者职责

  • PR 聚焦单一目标，改动建议控制在 400 行以内；过大时拆分为多个 PR。
  • 描述写清：改了什么、为什么改、如何验证；涉及 UI 时附截图或录屏。
  • 关联工单，标注风险点和需要重点看的地方。
  • 新增逻辑附带测试；无法测试的说明原因。
  • 回应每一条评论：修改后回复“已改”，不同意则说明理由，不要直接无视或私自标记已解决。
  • 评审开始后追加修改用新提交，便于评审者查看增量；合并前再整理。

评审者职责

重点关注

  • 正确性：边界条件、异常路径、并发
  • 设计：职责划分、是否与现有代码一致
  • 安全：输入校验、权限、敏感信息
  • 可维护性：命名、可读性、测试覆盖

行为约定

  • 对事不对人，针对代码提问而非评价作者
  • 指出问题时尽量给出理由或替代方案
  • 格式类问题交给 lint，不在评审中纠缠
  • 看不懂就问，不懂的代码不要批准

评论约定

评论使用前缀表明意图，避免提交者猜测哪些必须改：

前缀含义是否阻塞合并
[必须]缺陷、安全问题或违反规范，必须修改是
[建议]更好的写法，提交者可自行判断否
[疑问]需要提交者解释，可能引出修改视回答而定
[小问题]命名、拼写等细节否
[赞]值得肯定的写法否

合并规则

  • 合并前提：至少 1 个批准、所有 [必须] 评论已解决、CI 全绿、与 main 无冲突。
  • 默认使用 Squash and merge，合并后的提交信息即 PR 标题，需符合提交规范。
  • 需要保留多条有意义提交的 PR，可使用 Rebase and merge；禁止产生无意义的 merge commit。
  • 线上紧急修复可先合并后补评审，但须在 24 小时内完成补审并记录在工单中。
  • 禁止对 main 和 release/* 执行 push --force；个人分支使用 --force-with-lease。

05速查

# 1. 从最新主干拉分支
git switch main && git pull --rebase
git switch -c feat/PROJ-123-export-csv

# 2. 开发并提交
git add -p
git commit -m "feat(order): 支持按日期区间导出订单"

# 3. 同步主干并整理提交
git fetch origin
git rebase -i origin/main

# 4. 推送并创建 PR
git push -u origin feat/PROJ-123-export-csv

# 5. 合并后清理本地分支
git switch main && git pull --rebase
git branch -d feat/PROJ-123-export-csv
对本规范有修改建议，请直接向规范仓库提 PR，并按本文流程评审。
