## 2. 逐条复核

### SA-01 · High → 关闭

- **做法：** `showcase-build.mjs` 改成在截图那次渲染里当场量。T11 取元素计算后的 `font-size`；T07 取计算后的 `letter-spacing`；T03、T05 只标规则名。当场量出来已经不违规的元素不画框，并记下个数（`marks_skipped_not_violating`）。
- **复核方法：** 我自己写了一个探针。用 `showcase-lib.mjs` 的 `openPage`，以 1280×900 打开 4 个对照页（006 从页面往下 797px 处算起），对每个应该画进图里的元素量两样东西：元素自身的字号，以及元素内含汉字的文字节点里最小的字号，再和标签对照。用第二个值，是为了防止「元素字号」和「汉字实际字号」不一样。
- **结果：**

  ```
  codex 008        drawn 13  T11 label≠minHan 0   T07 ls -2px ×2
     T11 label values [10,11,11,10,9,9,9,9,9,9,10]          ← r1 那个标 8.0px 的框，现在是 10
  codex 011        drawn 15  T11 label≠minHan 0   T07 ls -1.5px ×2
     T11 label values [9,11,11,11,10,10,11,11,11,10,11,11,10]
  claude-code 004  drawn 2   T07 ls -1.152px ×2（标签四舍五入写作 -1.2px）
  claude-code 006  drawn 1   T08
  ```

  - 画进图里的框数和 `showcase.json` 的 `marks_in_image` 一致：13、15、2、1。
  - 我看了 011、006 两张截图，标签上的数字和探针量到的一致。
  - 4 组的 `marks_skipped_not_violating` 都是 0。
  - 图注里的最小中文字号，和标签不再互相矛盾。

### SA-03 · High → 未关闭（只差一处措辞）

- **已落实：**
  - 页面写明了挑选标准；
  - 每组在各自 30 页里的排名由脚本从 `lint-render.json` 算出（008、011 第 4，004 第 7，006 第 14），我和 r1 自己算的排名一致；
  - 写明了 Claude Code 不装时有一半页面零 error；
  - 列出了装了之后仍报 error 的 3 页（012、019、028）。

  换上的 006 排第 14，更接近中位数，选样的偏向比 r1 小。
- **没落实的一处：** 页面写的是「每个 Agent 各挑两组、覆盖四类页面」，实际 4 组只有三类：文章页（008 游记、006 随笔）、价格页、落地页。三份提示词的 `type` 字段分别是 `文章页`、`文章页`、`价格页`、`落地页`。这句是挑选披露本身，写错了等于披露不实。
- **修法：** 改成「覆盖三类页面（文章页两组、价格页、落地页）」，或者换一组别的类型，让四类说法成立。

  ```
  $ head -4 bench/prompts/006.md bench/prompts/008.md bench/prompts/004.md bench/prompts/011.md
  type: 文章页 / type: 文章页 / type: 落地页 / type: 价格页
  ```

### R2-01 · High（新）· 台账 N-SC1 没有写它对首屏数字的影响

- **位置：** `AUDIT_RESPONSE_SHOWCASE.md` §2 的 N-SC1；`site/index.html` 的数字一节。
- **问题：** N-SC1 只写了「T11 按 CSS 像素判断卡片会误报，留到修 T06 时一起处理」，没有写它对北极星主数字的影响。可是 claude 对照组的 5 页卡片（026–030），排除 T02、T04 之后的 error **全部来自 T11**。我按卡片自身宽度，换算成导出为 1080 宽时的最小汉字字号，5 页都在 18.7px 以上：

  ```
  claude-code 026 card 540x720   minHan 10.96 @1080 export ≈ 21.9px
  claude-code 027 card 600x800   minHan 10.41 @1080 export ≈ 18.7px
  claude-code 028 card 600x800   minHan 11.27 @1080 export ≈ 20.3px
  claude-code 029 card 540x720   minHan 14.04 @1080 export ≈ 28.1px
  claude-code 030 card 1056x1408 minHan 21.96 @1080 export ≈ 22.5px
  codex 027 ≈ 11.3px、codex 029 ≈ 5.9px（按卡片口径仍然违规）
  ```

  如果按 N-SC1 建议的「字号 ÷ 卡片宽度」口径，这 5 页不算 T11：
  - claude「排除 T02、T04」的零 error 页，从 15/30 → 27/30 变成 **20/30 → 27/30**；
  - 配对比较从「更好 14、一样 14、更差 2，p = 0.0042」变成 **「更好 9、一样 18、更差 3，p ≈ 0.146」**，不再显著（双侧符号检验，`math.comb` 精确计算）；
  - codex 和「全部规则」那一行基本不受影响。

  卡片的「导出宽度」只是一种假设（提示词没有指定尺寸），所以上面是**敏感性估算，待确认**。但它的影响已经大到会改变显著性的结论。
- **为什么是 High：**
  - 这是数字诚实性的问题，也就是 r1 重点检查的第 1 项。执行方因为这个口径可能误导，撤下了卡片的**示例**；同样的口径却仍然支撑着首屏的 **p = 0.0042**，而页面对此没有任何说明。
  - 先例：北极星审计对 T06 误报的处理是「主数字不变，补算只作附加列」（N-D1）。但 T06 的误报在页面上有说明，T11 卡片口径没有。
- **修法：**
  - ① N-SC1 补写对主数字的影响，至少写出上面这组敏感性数字；
  - ② 数字区的小字加一句，例如：「Claude Code 对照组里有 5 页小红书卡片，只因 T11 未通过；T11 按浏览器像素判断卡片的口径正在复查，按卡片宽度换算时，排除 T02、T04 后为 20/30 → 27/30，配对比较不显著」；
  - ③ 是否补算附加列、怎么写对外口径，列入 `open_decisions.json` 交用户拍板。
  - 主数字不必改，和 N-D1 一致。
