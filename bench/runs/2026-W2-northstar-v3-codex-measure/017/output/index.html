Git 使用规范

把约定写下来，把精力留给创造。
统一分支、提交与评审方式，让每一次变更都清晰、可追溯。

◎适用范围：团队所有代码仓库◷阅读约 6 分钟
↗
一个任务，一个分支，一次有意义的合并。

主分支始终保持可发布；所有变更通过 Pull Request（PR）评审后合入。

01

分支命名

BRANCH NAMING

从最新的 main 创建工作分支，使用小写英文与连字符。名称应说明变更目的，并关联任务编号，方便检索与追踪。

命名格式<type>/<issue-id>-<short-description>
分支类型、使用场景和命名示例
分支类型使用场景命名示例
feat新增功能feat/128-user-login
fix修复缺陷fix/256-token-expiry
refactor重构现有实现refactor/312-auth-service
docs更新文档docs/108-api-guide
chore构建、依赖与维护chore/420-update-lint
ⓘ

主分支保护：禁止直接推送或强制推送到 main。分支保持短期存活，合并完成后删除；没有任务编号时可省略编号。

从一个干净的分支开始 ＋

确认工作区干净，再更新主分支并创建工作分支。

git switch main
git pull --ff-only origin main
git switch -c feat/128-user-login
02

提交信息

COMMIT MESSAGES

一次提交只做一件事。使用统一的提交格式，让历史记录能直接回答“改了什么”，必要时在正文解释“为什么”。

提交格式 · scope 可选<type>(<scope>): <description>
一个清晰的提交
feat(auth): 支持邮箱验证码登录

为未设置密码的用户提供登录入口。
新增验证码有效期与重试次数校验。

Refs: #128

写清楚变更

  • 类型沿用分支类型，测试使用 test，性能优化使用 perf。
  • 描述以动作开头，如“修复”“新增”“移除”；标题建议控制在 72 字符内。
  • 有不兼容变更时，在类型或作用域后加 !，并在正文说明迁移方式。

↘ 避免含糊的提交

updatefix bug修改一下

更好的写法

fix(auth): 修复令牌过期后无法退出的问题
03

代码评审

CODE REVIEW

作者对变更质量负责，评审者对合并质量把关。尽量让每个 PR 聚焦单一目标；大改动先拆分，或提前对齐设计。

  1. 1

    先自查，再发起 PR 作者

    检查差异，移除调试代码与敏感信息，运行相关测试。未准备好评审时，使用 Draft PR。

  2. 2

    交代背景与验证方式 作者

    标题沿用提交格式；描述包含变更原因、主要改动、关联任务、测试结果与风险。界面变更附前后截图，必要时补充回滚方案。

  3. 3

    邀请评审，逐项回应 作者 + 评审者

    至少邀请一位熟悉模块的同事，建议在一个工作日内首次响应。优先检查正确性、边界条件、可维护性与测试；明确区分必须修改的问题和可选建议。

  4. 4

    通过检查后合并 合并负责人

    获得至少一位非作者的批准，所有必需 CI 检查通过，阻塞问题解决后，使用 Squash merge 合入。核对最终提交信息，删除工作分支。

评审后又有修改？

推送修复后说明改动，并重新请求评审。新增实质性变更需要重新批准；发生冲突时，由作者解决并重新运行检查。

04

合并前，再确认一次

准备好把这次变更交给团队了吗？

0 / 5 已完成

清单仅辅助本次自查，不替代仓库中的审批与自动检查。
