1. 总体原则

  • 主干受保护：main 分支禁止直接推送，所有变更必须经由合并请求（PR / MR）进入。
  • 小步快跑：分支生命周期尽量短（建议不超过 3 个工作日），PR 尽量小（建议 400 行以内的有效改动）。
  • 历史可读：每个提交表达一个完整、独立的意图，提交信息说明“做了什么、为什么”。
  • 评审是协作而非审判：对事不对人，目标是共同提升代码质量与知识共享。

2. 分支命名

2.1 分支模型

我们采用基于主干的轻量分支模型：长期分支只有 main（可选 release/*），其余均为短期分支，完成即删除。

分支用途从哪里创建合并到生命周期
main随时可发布的稳定代码——长期
feature/*新功能开发mainmain短期
fix/*常规缺陷修复mainmain短期
hotfix/*线上紧急修复main 或对应 release/*main（及 release）短期
release/*发布准备与版本维护main打 tag，必要时回合 main按版本
refactor/* docs/* chore/*重构 / 文档 / 构建与杂项mainmain短期

2.2 命名格式

<类型>/<任务编号>-<简短描述>

feature/PROJ-123-user-login
fix/PROJ-456-order-total-rounding
hotfix/PROJ-789-payment-timeout
release/2.4.0
docs/update-readme-setup
  • 全部使用小写英文，单词之间用连字符 - 分隔。
  • 有任务 / Issue 时必须带编号，方便与需求系统自动关联；纯杂项可省略。
  • 描述控制在 2–5 个单词，体现“做什么”，不写人名、日期。
  • release 分支使用语义化版本号：release/主版本.次版本.修订号。

✓ 推荐

  • feature/PROJ-102-export-csv
  • fix/PROJ-88-null-avatar-crash
  • chore/upgrade-node-20

✗ 避免

  • zhangsan-dev（人名，无意义）
  • Feature/ExportCSV（大写、驼峰）
  • fix_bug（下划线，描述模糊）
  • 新功能-导出（中文，部分工具兼容差）

2.3 使用规则

  • 开始工作前先同步：git switch main && git pull --rebase，再创建分支。
  • 一个分支只做一件事；发现无关问题请另开分支。
  • 开发期间定期用 git rebase main 同步主干，减少最终冲突。
  • 个人分支在推送 PR 之前可自由整理历史；PR 进入评审后避免强推，如必须强推请使用 --force-with-lease 并在 PR 中说明。
  • 合并后删除远程分支（平台上勾选“合并后删除分支”）。

3. 提交信息

采用 Conventional Commits 约定，便于生成变更日志和自动判断版本号。

3.1 格式

<type>(<scope>): <subject>
                                    ← 空一行
<body>
                                    ← 空一行
<footer>
部分是否必填要求
type必填变更类型，见下表
scope可选影响范围，如模块名 auth、order、api
subject必填一句话概括，≤ 50 字符；中英文均可但仓库内保持统一；英文用祈使句、首字母小写、结尾不加句号
body建议说明为什么改、改动思路与影响；每行 ≤ 72 字符
footer按需关联任务 Refs: PROJ-123、关闭 Issue Closes #45、不兼容变更 BREAKING CHANGE: ...

3.2 type 列表

type含义是否出现在变更日志
feat新增功能是（次版本号 +1）
fix修复缺陷是（修订号 +1）
perf性能优化是
refactor重构，不改变外部行为否
docs仅文档变更否
style格式调整（空格、分号等），不影响逻辑否
test新增或修改测试否
build构建系统、依赖变更否
ciCI 配置与脚本否
chore其他杂项否
revert回滚之前的提交视情况

不兼容变更：在 type 后加 !（如 feat(api)!: ...），并在 footer 写 BREAKING CHANGE: 说明迁移方式，主版本号 +1。

3.3 示例

feat(auth): 支持手机号验证码登录

原有登录仅支持账号密码，移动端转化率偏低。
新增短信验证码登录方式，验证码 5 分钟有效，
同一手机号 60 秒内只能请求一次。

Refs: PROJ-123
fix(order): correct total rounding for multi-currency carts

Totals were rounded per line item, causing 0.01 drift when
summed. Round only once at the cart level.

Closes #456
feat(api)!: 移除 v1 用户查询接口

BREAKING CHANGE: /api/v1/users 已删除，请改用 /api/v2/users，
返回结构中 name 字段拆分为 firstName 与 lastName。

✓ 好的 subject

  • fix(cart): 修复空购物车结算时报错
  • refactor(user): extract address validator

✗ 差的 subject

  • update / 修改 / fix bug
  • WIP、temp、aaa
  • 修复登录、调整样式、升级依赖（多件事混在一起）

3.4 提交习惯

  • 原子提交：一个提交只做一件事，且每个提交都能通过编译与测试。
  • 格式化、重命名等机械改动与逻辑改动分开提交，方便评审。
  • 提交前用 git diff --staged 自查，不提交调试代码、注释掉的代码、密钥与本地配置。
  • 推送 PR 前，可用 git rebase -i main 合并 “fix typo”“wip” 等零碎提交。
  • 建议在仓库中配置 commitlint + Git hooks，自动校验提交信息格式。

4. 代码评审流程

4.1 流程步骤

  1. 自测与自查本地通过构建、单元测试和 Lint；通读一遍自己的 diff，删除无关改动。
  2. 创建 PR标题沿用提交信息格式（如 feat(auth): 支持验证码登录），按模板填写描述；未完成时标记为 Draft。
  3. CI 通过CI 全绿后再请求评审；CI 失败的 PR 评审人可不予处理。
  4. 指派评审人至少 1 名评审人，涉及核心模块、数据库变更或安全相关时至少 2 名，并包含模块 Owner（参考 CODEOWNERS）。
  5. 评审与讨论评审人在 1 个工作日内给出首次反馈；作者逐条回复或修改，修改后重新请求评审。
  6. 批准与合并获得所需数量的 Approve、所有讨论已解决、CI 通过后，由作者本人合并并删除分支。
  7. 跟进验证合并后关注部署与监控，确认需求系统中任务状态已更新。

4.2 作者须知

PR 描述模板：

## 背景
为什么要做这个改动？关联任务：PROJ-123

## 改动内容
- 新增 xxx
- 调整 yyy 的处理逻辑

## 测试方式
- [ ] 单元测试已覆盖
- [ ] 本地手动验证步骤：...

## 影响范围 / 风险
是否涉及数据库迁移、配置变更、接口兼容性？

## 截图（UI 改动必填）
  • PR 保持小而聚焦；大功能拆分为多个可独立合并的 PR（可借助功能开关）。
  • 对不直观的设计决策，主动在代码旁留下评论解释，降低评审成本。
  • 不同意评审意见时，说明理由并讨论；无法达成一致时请 Tech Lead 裁决，避免长时间僵持。

4.3 评审人须知

评审关注点（按优先级）：

  • 正确性：是否实现了需求？边界条件、异常处理、并发问题是否考虑？
  • 安全性：输入校验、权限控制、敏感信息是否泄露？
  • 设计：职责划分是否合理？是否引入不必要的复杂度或重复代码？
  • 可测试性：关键逻辑是否有测试覆盖？测试是否有意义？
  • 可读性：命名、结构、注释是否清晰？他人能否快速理解？
  • 性能：是否有明显的 N+1 查询、无界循环、内存泄漏？

评论时使用前缀标明意图，让作者清楚哪些必须处理：

前缀含义是否阻塞合并
[必须]缺陷、安全问题或违反规范，必须修改是
[建议]更好的写法或设计，作者自行判断否
[疑问]需要作者解释，可能引出修改视回复而定
[小问题]命名、拼写等细节（nit）否
[赞]值得肯定的写法，鼓励分享否
  • 评论针对代码而非个人：用“这里可能会……”代替“你写错了”。
  • 提出问题时尽量给出原因或替代方案。
  • 纯格式问题交给 Lint / Formatter，不在评审中反复讨论。
  • 单次评审建议不超过 60 分钟；PR 过大时可要求作者拆分。

4.4 合并规则

场景合并方式说明
常规 feature / fix PRSquash and merge主干每个 PR 对应一个提交，提交信息使用 PR 标题，保证符合规范
提交历史已精心整理的 PRRebase and merge保留每个原子提交，需事先在 PR 中说明
release / hotfix 回合主干Merge commit保留分支合并痕迹，便于追溯版本

紧急修复例外：线上 P0 故障可先由 1 名评审人快速批准后合并，但须在 24 小时内补充完整评审与复盘记录。

5. 常用命令速查

# 开始新任务
git switch main
git pull --rebase
git switch -c feature/PROJ-123-user-login

# 提交
git add -p                      # 分块挑选要提交的改动
git commit                      # 在编辑器中书写完整提交信息

# 同步主干
git fetch origin
git rebase origin/main

# 整理提交（仅限尚未进入评审的个人分支）
git rebase -i origin/main

# 推送
git push -u origin HEAD
git push --force-with-lease     # 必须强推时使用，切勿使用 --force

# 合并后清理
git switch main && git pull --rebase
git branch -d feature/PROJ-123-user-login
git fetch --prune
本规范由团队共同维护。修订请提交 PR 到文档仓库，并遵循本文档自身的提交与评审流程。
